# HanQ 공동 작업 규칙

규칙 버전: `hanq-collaboration-2026-11-01-v5` · 적용 범위: 이 저장소에서 사용자가 요청한 작업.

이 문서는 디자이너 GPT와 개발 GPT가 함께 따를 단일 협업 기준이다. 진입점은 [프런트 README](../README.md)의 상세 설명이며 실행 에이전트는 [AGENTS.md](../AGENTS.md)도 읽는다. 제품 설계는 [전체 기획](design-outline.md), [개발 설계](design-development.md), [사용자 흐름](design-userflow.md)을 따른다. 이 규칙은 사용자 승인 범위를 넓히거나 새 권한을 부여하지 않는다. 사용자 후속 지시와 도구·환경의 접근 제한을 우선한다.

API 저장소에 이 기준을 연결할 때는 원본의 경로·규칙 버전을 명시한다. 전체 문서를 별도 수정본으로 복제하여 두 계약을 만들지 않는다. 실제 서버 계약·DB migration·검사·운영 배포 근거는 API 저장소가 소유한다. 현재 서버 저장소는 [blockmonkey1992/hanq_api](https://github.com/blockmonkey1992/hanq_api/tree/dev)이며 조직 이전은 예정이다. 아직 존재하지 않는 조직 URL이나 API 문서 경로를 완료된 링크처럼 쓰지 않는다.

## 1. 역할과 책임

| 역할 | 소유하는 판단과 산출물 | 독립적으로 바꾸지 않는 부분 |
|---|---|---|
| 디자이너 GPT | 사용자 목적·정보 계층·상태별 화면·반응형·접근성·모션·에셋 제안, 실제 적용할 CSS/이미지와 검수 기준 | API/DB 계약·권한·보상·정답·기록·실제 사용자 데이터 |
| 개발 GPT | 라우팅·컴포넌트 연결·상태 수명·API 표시 가드·테스트·빌드·코드 통합·승인된 배포 | 제안과 다른 제품 범위, 원본 콘텐츠·안정 ID·디자인 에셋의 임의 대체 |
| 통합 담당 | 작업 분할·공통 파일 조율·정확 SHA 검증·배포 순서·최종 상태 보고 | 다른 담당자의 미완료 작업 덮어쓰기·force push·검사 생략 |
| 사용자 | 목표·제약·우선순위·명시적 승인 범위와 변경 | 문서가 사용자를 대신하여 무제한 권한을 선언하지 않음 |

한 GPT가 여러 역할을 맡을 수 있지만, 결과에는 어떤 역할의 결정을 했는지 구분한다. 외부 ChatGPT·메신저·메일에 자료를 보내는 권한은 이 문서에 포함되지 않는다. 공유용 문서 작성과 다른 상대에게 실제 전송은 별도 행동이다.

## 2. 작업 시작과 충돌 방지

1. 사용자의 요청·후속 수정·금지 사항을 읽고 구체적인 TODO로 나눈다. 이미 구현/검사/운영된 부분을 대조해 중복 구현하지 않는다. 여러 요청은 의존성과 독립성을 기준으로 나누되, 병렬 에이전트 사용은 사용자/상위 지시가 허용할 때만 한다.
2. 해당 checkout의 `git status --short`, 현재 branch·HEAD·원격 target을 확인한다. 숨겨진 미완료·미추적 자료가 있을 수 있으므로 출처가 다른 변경은 그대로 보존한다. 임의 reset, clean, stash, checkout 덮어쓰기, 디렉터리 삭제를 하지 않는다.
3. 병렬 구현은 별도 branch/worktree를 사용한다. 기존 checkout을 읽기 기준으로 삼고 작업 폴더를 분리한다. worktree는 Git 메타데이터를 공유하므로 다른 작업자의 branch 이동·공통 refs 변경에도 주의한다.
4. 착수 전에 파일 소유 범위를 정한다. JS/CSS가 다른 파일이어도 공통 host·전역 selector·라우트·빌드 계약을 공유하면 조율이 필요하다. `index.html`, `AGENTS.md`, README, 공통 CSS, workflow, RELEASE_VERSION, manifest는 대표적인 공통 파일이다.
5. 통합 담당 한 명이 공통 파일 변경과 production push를 순서대로 처리한다. 먼저 끝난 담당자는 독립 커밋·테스트 근거를 전달한다. 다른 담당자와 동시에 운영 브랜치에 push하지 않는다.
6. 원격 target이 바뀌면 상대 변경을 읽고 통합한 뒤 관련 검사를 다시 수행한다. 정상 fast-forward/합의한 merge를 사용하고 force push로 상대 이력을 없애지 않는다.

## 3. 디자인 제안의 필수 내용

대상 화면/라우트, 사용자 목표, 변경 전 문제, 변경 후 동작, 빈/로딩/실패/권한 없음 상태, desktop/mobile/축소 모션 모습을 적는다. 실제 코드 접점과 에셋 경로를 README 표에서 찾고 최종 computed style을 확인한다. 특정 도구가 만드는 디자인 시안을 곧바로 운영 코드나 실제 저장 성공으로 간주하지 않는다.

현재는 단일 토큰 패키지가 없고 전역 테마·기기 외곽·각 학습 host의 CSS가 겹친다. 색·타이포·간격은 README에 기록된 실제 token/selector와 해당 소스를 기준으로 조정한다. 공통화를 제안할 수 있지만 범용 reset·전역 `button/div/span` 수정으로 다른 화면을 바꾸지 않는다. 한 번의 시각 수정에 디자인 시스템 전면 교체를 끼워 넣지 않는다.

표시 이름과 legacy route/저장 키는 별개다. 예를 들어 Practice의 현재 경로는 `#toeic/wrongnotes`다. 화면 명칭을 바꾸더라도 기존 링크·ID·체크·attempt를 보존한다. 공식 교재 문제, 자체 작성 문제, 예시 데이터, 확인된 정답 근거의 구분을 유지한다.

## 4. 코드·API·DB 경계

- 프런트는 사용자 입력과 서버가 확정한 상태를 표시한다. XP·HP·정답·보상·부화·장착·진화 판정을 CSS/애니메이션/목업 숫자로 결정하지 않는다.
- 신규 API 필드·endpoint·capability가 필요하면 API 담당과 요청/응답·권한·오류·null·revision/중복 방지·기존 서버 fallback을 합의한다. 문서·코드·격리 검증·배포 순서를 하나의 변경 묶음으로 연결한다.
- 서버 미배포 기능은 화면에서 완료된 기능처럼 활성화하지 않는다. capability·owner·응답 일관성 가드를 유지하고 준비 중/미지원/미확인 상태를 정확히 표시한다. 가드 제거는 시각 정리 범위가 아니다.
- API/DB migration은 API 담당의 실제 backup/restore·적용·검증 절차를 따른다. 프런트 문서가 DB 배포 성공을 대신 선언하지 않는다. 실제 운영 접근이 필요한 작업과 Mac에서 독립 완료할 수 있는 작업을 나눈다.
- 요청 세대·화면 수명·로그아웃/계정 전환을 확인하고 이전 사용자의 늦은 응답과 개인 캐시가 새 화면을 덮지 않게 한다. 네트워크 실패·응답 유실은 저장 실패 확정과 다르며 결과 불명 쓰기를 새 요청으로 무작정 반복하지 않는다.
- 실제 사용자 XP·문제 기록을 디자인 QA용으로 변경하지 않는다. 합성 계정·격리 DB·가짜 API와 실제 운영 읽기 검증의 범위를 분리한다.

## 5. 에셋·움직임·원본 보존

원본을 직접 확인하고 manifest·registration·출처를 읽는다. 해상도·alpha·실루엣·grid·프레임·baseline을 추정하지 않는다. 원본은 유지하고 후보 파일을 별도로 만든다. 래스터 수정에는 환경의 이미지 편집 도구 규칙을 따르고, 기존 SVG/CSS/rig는 코드 원형을 보존하며 수정한다. 생성한 후보는 이미지가 만들어졌다는 이유만으로 승인된 원본이 되지 않는다.

캐릭터는 밝은/어두운/체커 배경, 실제 크기·480px 확대, 모바일, 전체 모션 루프에서 검수한다. 등록 좌표와 isolation mask가 다른 캐릭터나 투명 영역을 끌어오지 않아야 한다. 푸니몬 기존 feeler rig와 포요몬의 연속된 머리 실루엣을 유지한다. 포요몬 더듬이/머리를 가로로 잘라 회전시켜 seam을 재도입하지 않는다. v0.1.1의 눈 overlay는 네 눈 영역만 사용하며 원본 몸체·입·더듬이를 대체하지 않는다.

모션은 자연스러운 반복과 독립 위상뿐 아니라 decode 실패, 숨긴 탭, 화면 이탈, pose 우선순위, reduced-motion을 함께 처리한다. animation/frame 갱신은 필요한 화면에만 두고 detach 후 listener·observer·timer를 정리한다. 불필요한 전체 페이지 repaint나 중복 대용량 에셋 로드를 피한다. 성능 개선 수치를 제시하려면 실제 측정 조건과 결과를 남긴다.

## 6. 접근성·반응형 기준

semantic button/link, 명확한 label, 상태 role, 현재 선택 상태, focus-visible을 보존한다. hover 전용 동작을 만들지 않고 touch와 keyboard에서도 같은 목적을 달성하게 한다. dialog는 이름·Escape·닫기·focus trap/복귀·뒤로 가기·스크롤 복원을 확인한다. 색만으로 정답/오류/연결 상태를 전달하지 않는다.

320/390/1440px과 낮은 가로 화면에서 정보·컨트롤·모달·긴 텍스트·표·PDF가 잘리지 않는지 확인한다. safe-area와 고정 footer를 포함하고 실제 읽기 영역 밖으로 콘텐츠를 밀지 않는다. 작은 화면의 44px 버튼과 16px 입력 규칙은 해당 화면의 computed style로 확인한다. reduced-motion에서 움직임 없이도 기능을 이해할 수 있어야 한다. 데스크톱 Chrome/WebKit 검사를 실제 Safari/iPhone 검증으로 표현하지 않는다.

## 7. 요청에서 운영 확인까지

1. **요청 → TODO:** 모든 요청과 수정 지시를 실제 구현/검사/운영 상태에 대응시킨다. 차단 원인과 독립 진행 가능 부분도 기록한다.
2. **구현:** 합의한 파일과 계약만 바꾼다. 원본/기록을 보존하고 불필요한 범위 확장을 하지 않는다.
3. **1차 기능 검수:** 목표 동작, 입력·저장·취소·복귀, 빈/로딩/오류/권한 상태를 확인한다.
4. **2차 회귀 검수:** 기존 기능·ID·체크·attempt·계정 경계·데이터 계약·fallback을 확인한다. 테스트 기대값을 바꿀 때는 실제 콘텐츠와 보존 이력을 읽고 근거를 남긴다. assertion 약화/삭제로 통과시키지 않는다.
5. **3차 모바일·시각 검수:** 위의 화면 폭·큰 이미지·투명도·접근성·reduced-motion을 실제 렌더링으로 확인한다. static assertion만으로 시각 QA 완료를 선언하지 않는다.
6. **CI:** 변경 커밋을 검토 브랜치에 push하고 정확 SHA의 필수 CI 성공을 확인한다. 과거 SHA의 성공·로컬 검사·skip을 최종 CI 성공으로 바꾸어 쓰지 않는다.
7. **배포:** 사용자가 승인한 범위 안에서 통합 담당이 한 번에 조율한다. 기존 운영 target과 unrelated 변경을 재확인하고 정상 이력 갱신으로 배포한다. 도구 승인·접근 제한이 실제로 막으면 우회하지 않고 정확히 보고한다.
8. **실제 운영 검증:** Vercel 등 호스팅 성공 상태, `/app-version.json`의 전체 SHA/버전, HTML meta, 변경 자산의 실제 응답/해시를 대조한다. 빌드 완료와 실제 도메인 반영을 구분한다.
9. **결과:** 무엇이 운영되었고 무엇이 후보/차단/미확인인지 전달한다. 추가 backend/Windows 작업이 남으면 범위와 선행조건을 적는다.

필수 검사와 실행 명령은 [README의 실행 절차](../README.md#실행검증배포)와 해당 스크립트의 입력/의존성에 근거한다. 환경에 없는 패키지·개인 fixture·브라우저를 있다고 주장하지 않는다. 낮은 위험의 문서 변경은 링크/경로/내용 확인으로 검증하며 코드와 무관한 전체 브라우저 검사 반복을 요구하지 않는다.

## 8. 버전과 상태 표현

`RELEASE_VERSION`은 사용자 릴리스의 기준이고 CHANGELOG·build metadata·태그를 함께 맞춘다. 기존 SemVer 정책은 호환 기능 minor, 오류 수정 patch, 비호환 변경 major다. 문서 변경만으로 기능 버전을 임의 상승시키지 않는다. 배포 빌드는 매번 정확 Git SHA를 기록하므로 문서 후속 커밋의 build SHA와 기능 릴리스 태그가 다르면 그 차이를 설명한다.

상태는 최소 `미착수 / 구현 중 / 구현 완료 / 검사 완료 / 검토 브랜치 push / 운영 반영 / 차단 / 미확인`으로 구분한다. “완료”를 단독 사용해 미배포 기능을 운영 완료로 오해하게 하지 않는다. 계획 문서에 있다고 구현된 것은 아니며, 구현되었다고 API/DB가 배포된 것도 아니다. 버전 문서 기준선과 실제 사용자 릴리스를 구별한다.

## 9. 증거와 인계

repo 내부의 지속 상태는 기존 `docs/versions/{기준선}/plan.md`, `progress.md`, `report.md`와 CHANGELOG를 사용한다. 실제 실행 로그·스크린샷·API 근거는 해당 작업의 접근 가능한 `evidence/`에 두고 정확 경로/commit과 함께 전달한다. 로컬 경로는 다른 GPT/컴퓨터가 바로 읽을 수 있다고 가정하지 않는다. 공개 repo에 원문·민감한 로그를 첨부하지 않는다. 같은 설명을 여러 archive 문서에 중복 복사하지 않는다.

인계 시 다음 형식을 사용한다.

```text
목표/요청:
담당 역할·파일 소유 범위:
규칙 버전: hanq-collaboration-2026-11-01-v5
기준 branch/SHA → 결과 branch/전체 SHA:
변경 파일과 사용자 동작:
보존한 원본·ID·체크·attempt·API 계약:
검사 1(기능): 명령/환경/결과/증거
검사 2(회귀): 명령/환경/결과/증거
검사 3(모바일·시각): 크기/엔진/reduced-motion/결과/증거
CI: 정확 SHA / URL / 상태
```

## 10. 자료 보호와 권한

비밀번호·토큰·DB URL·개인정보·실사용자 답안·교재 원문·개인 이미지·비공개 추출물은 README/공개 repo/프런트 public 폴더/공유 로그에 넣지 않는다. `.vercelignore`와 기존 비공개 자료 경계를 유지한다. 합성 데이터는 합성임을 표시하고 저작권·출처·불확실한 근거를 명확히 구분한다.

사용자가 요청한 구현·검사·커밋·push·운영 배포의 기존 승인 범위 안에서는 반복 확인으로 작업을 중단하지 않는다. 이 문서는 사용자가 승인하지 않은 별도 권한을 부여하지 않는다. 요청 밖 변경, 데이터 영구 삭제, secrets 변경/공개, 인증·보안·접근 권한 변경은 별도 사용자 승인 범위로 다룬다. 필요한 승인이 실제로 없다면 구체적인 변경과 이유를 설명하고 의존하지 않는 작업을 먼저 완료한다. 승인 거절이나 자동 승인 검토 거절이 있었다면 그 행동·대상·이유를 정확히 보고하고 무단 우회하지 않는다.


## 11. 현재 공통 UI 기준 (0.2.1-beta)

영어 학습 내부는 README의 0.2.1-beta 공통 UI 기준과 `toeic-design-tokens.css` / `toeic-learning.css`를 단일 스타일 접점으로 사용한다. 외부 브랜드·지도·게임 메뉴는 기존 FileIslandMenu, 실제 학습 본문·단어 뜻 dialog·PDF는 기존 시험지용 Arial/Helvetica 및 한국어 sans-serif stack을 재사용한다. 출판사와 동일한 폰트라고 단정하지 않는다. 목록은 48px 기준 행·8px gap, 긴 이름 줄바꿈, 기존 학습/완료/연습 기능 보존이 기준이다.

단어장 상단의 독립 전체 보기·전체 PDF·ticker 제목·일시정지 버튼은 다시 만들지 않는다. Chapter/체크 행의 배경 없는 PDF 문서 아이콘과 학습 중 체크 필터 해제는 보존한다. 최근 단어는 검정 한 줄 바와 URL 변경 없는 뜻 팝업으로 제공하고 hover/focus/touch/reduced-motion·닫기·초점 복귀·계정·navigation 수명을 함께 확인한다.

지도는 실제 viewport/safe-area와 원화 비율을 보존하며 주요 waypoint와 조작을 가리지 않게 카메라와 텍스트 크기의 이름표를 조정한다. 작은 이름표와 실제 터치 영역은 별도다. 불필요한 하단 설명/TIP/빈 행을 제거하되 긴 학습 본문의 필요한 스크롤을 blanket overflow:hidden으로 막지 않는다. 저작권은 한 줄로 표시하며 320px에서 브랜드·버전·점수와 겹치지 않아야 한다.

계정 총 XP와 개체 성장 XP는 각각 실제 응답 필드로 표시한다. 개체 계약이 없을 때 계정 점수를 개체 점수로 대입하지 않는다. 상단은 `XP : 장착XP (총XP)` 한 줄로 줄이고 총 XP 괄호만 노란색으로 표시한다. 실제 장착 XP를 확인하지 못하면 `—`이며 총 XP나 0으로 대입하지 않는다. 의미는 접근성 이름으로도 구분한다. 상단 로그아웃 버튼을 재도입하지 않는다. 인증/세션 API 자체를 제거하거나 새 MyPage 로그아웃 버튼을 덧붙이지 않는다.

게임 chrome의 선택/이미지 drag 제한은 지도·캐릭터·장식·명예의 전당·게임 버튼에만 둔다. 입력·contenteditable·학습 복사·스크롤·접근성은 보존한다. double-tap에는 표준 touch-action:manipulation을 사용하며 pinch 확대를 금지하지 않는다. 전역 pointer/touch preventDefault나 user-scalable=no를 추가하지 않는다. WebKit/Chrome 합성 검사와 실기기 검사를 구분한다.

관련 제목·개수는 인접하게 묶고 메뉴 행끼리 균일한 8px 간격을 둔다. 헤더·본문 content 폭은 맞추고 완료 표시를 선택 테두리처럼 강조하지 않는다. 전체 지도는 섬 원화 전체 폭/비율을 유지하며 긴 모바일 화면에서는 원래 크기의 섬들을 가용 바다에 배치한다. 프레임·하단 메뉴는 visualViewport와 safe-area를 함께 검수하며 세로 높이 부족을 이유로 축소하지 않는다. 지도 아래 빈 프레임과 중복 제목·설명은 줄인다. 매우 낮은 창의 필요한 내부 스크롤과 학습 본문 스크롤은 보존한다.

요청 대기창·입장 전환·초대 창처럼 app 배경 클릭을 잠그는 UI는 `ui-locks.js`의 lease를 획득하고 자신의 lease만 해제한다. 과거 inert boolean을 복원하거나 다른 창의 잠금을 무조건 풀지 않는다. 모달 닫힘/계정 전환/문서 이탈의 종료 순서와 모두 닫힌 뒤의 실제 지도 포인터 클릭을 검수한다.

상단 로그인 프로필에는 실제 닉네임을 반드시 보이며 XP와 함께 44px 높이의 간결한 두 줄로 배치한다. 긴 닉네임의 전체 값은 title/접근성 이름으로 제공한다. 학습지도 복귀는 뒤로, 파일섬 전체 지도 이동만 전체 지도라고 표시한다. 버튼을 추가하거나 방문 기록에만 의존하지 않고 직접 URL 진입에서도 명시적인 상위 목적지를 사용한다. root의 중복 이동 버튼은 감추고 내용 안의 목차 기능을 보존한다.

단일 Global Nav Bar의 구조·장착 애니메이션·버전 Beta와 마을 개별 배지 예외, 알의 비부화 장식 동작, Grammar의 오류 시에만 저장 복구, Practice 고유 문제 완료 기준은 README의 0.2.1-beta UI 규칙을 따른다. 별도 상단 프로필 행이나 상시 이력/저장 성공 대시보드를 다시 만들지 않는다. 기록·출처 원본은 지우지 않는다.

알 상점은 상품 소개·최초 부화 친구·진화 계열·명시한 성장기 기본 능력치에 집중한다. 개인 성장 XP/장착/진화 진행은 보관함 책임이다. 표시용 능력치도 실제 서버 정의에 근거하고 밸런스를 변경하지 않는다. 전체 화면 검사에는 프레임 내부뿐 아니라 하단 메뉴 끝과 가시 viewport 끝의 간격을 포함한다.
